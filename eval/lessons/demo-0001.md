# Lesson: DEMO - Indonesian thousands separator misread as a decimal

This file is a demonstration of the change-request flow. It was not produced by a
real scan. Close or delete this pull request once you have seen it.

- Lesson id: demo-0001
- File: sample-supermarket.jpg (synthetic)
- Created: 2026-10-08

## What was wrong

The total on this receipt is printed as `129.000` (Indonesian thousands, Rp
129,000). One structuring config returned `129`, treating the dot as a decimal
point. That value was not present in the OCR tokens, so the verifier nulled it
and flagged `total:not_in_ocr`. The other configs were correct.

## What zippp read

- paddle-flash (paddle PP-OCRv6 deepseek-flash): merchant Toko Sumber Jaya, date
  2026-10-05, total 129000, 3 item(s), flags []
- paddle-pro (paddle PP-OCRv6 deepseek-v4-pro): merchant Toko Sumber Jaya, date
  2026-10-05, total 129, 3 item(s), flags [total:not_in_ocr]
- gemini-flash (gemini PP-OCRv6 gemini-2.5-flash): merchant Toko Sumber Jaya,
  date 2026-10-05, total 129000, 3 item(s), flags []

## Diagnosis

The failure is in number normalization on the structuring side: a lone dot with
three trailing digits must be treated as a thousands separator, not a decimal
point. The verifier already catches it, which is why the dangerous number is
still zero.
